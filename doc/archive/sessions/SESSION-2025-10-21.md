# Development Session - 2025-10-21

## Summary

This session focused on fixing service shutdown behavior, implementing fast-fail functionality, and adding proper Ctrl+C signal handling to TestMe.

## Issues Addressed

### 1. Service Shutdown Timeout Not Working

**Problem**: The `/Users/mob/c/url/test/setup.sh` script's signal handler was not executing when TestMe stopped the service.

**Root Cause**: When `shutdownTimeout=0` (the default), the code was skipping SIGTERM entirely and sending only SIGKILL, which prevented signal handlers from running.

**Solution**:
- Modified `killProcessUnix()` and `killProcessWindows()` in `src/platform/process.ts`
- Always send SIGTERM first when `graceful=true`, regardless of timeout value
- Implemented polling mechanism: check every 100ms if process exited
- With `shutdownTimeout=0`: Send SIGTERM → wait 100ms → SIGKILL if still running
- With `shutdownTimeout>0`: Send SIGTERM → poll every 100ms → SIGKILL only if still running
- Changed default from 0 to 5 seconds for optimal behavior

### 2. Ctrl+C Not Stopping TestMe

**Problem**: Pressing Ctrl+C would stop the current test but TestMe would continue running remaining tests.

**Solution**:
- Added `setupSignalHandlers()` method to TestMeApp class
- Implemented `shouldStop` flag and `interruptCount` tracking
- First Ctrl+C: Sets flag, prints warning, stops gracefully
- Second Ctrl+C: Forces immediate exit with code 130
- Added callback mechanism to TestRunner to check `shouldStop` before each test
- Stop checks added at: configuration group loop, sequential test loop, parallel worker loop

### 3. Fast-Fail Feature Request

**Problem**: No way to stop immediately when a test fails (fast-fail behavior).

**Solution**:
- Added `--stop` CLI option
- Added `stopOnFailure` flag to ExecutionConfig
- Sequential mode: `break` on first failure
- Parallel mode: Shared `shouldStop` flag clears queue and stops workers
- Help text and examples updated

## Key Design Decisions

1. **shutdownTimeout Default = 5 seconds**
   - Rationale: With polling, no penalty for higher default (exits fast if service exits quickly)
   - User can still override to 0 for immediate force-kill

2. **Polling Interval = 100ms**
   - Balances responsiveness vs CPU usage
   - Gives signal handlers time to execute even with timeout=0

3. **Two-Stage Ctrl+C**
   - First press: Graceful stop (complete current test, run cleanup)
   - Second press: Force quit (immediate exit)
   - Standard behavior expected by users

4. **Callback Pattern for shouldStop**
   - Avoids tight coupling between TestMeApp and TestRunner
   - TestRunner doesn't need direct reference to TestMeApp
   - Clean separation of concerns

## Lessons Learned

1. **Always send SIGTERM first**: Even with timeout=0, give processes a chance to clean up
2. **Polling > Blind Wait**: Detecting process exit dynamically is better than fixed delays
3. **Progressive Interrupts**: Two-stage Ctrl+C handling provides escape hatch while being user-friendly
4. **Callback Pattern**: Using callbacks for cross-component communication keeps code decoupled

## Technical Notes

### Signal Numbers
- SIGTERM = 15 (Unix graceful termination)
- SIGKILL = 9 (Unix force kill)
- SIGINT = 2 (Ctrl+C)
- Exit code 130 = 128 + 2 (terminated by SIGINT)

### Process Management
- Windows: `taskkill /PID` (graceful) vs `taskkill /F /PID` (force)
- Unix: `kill -TERM` (graceful) vs `kill -KILL` (force)
- Process check: Different implementations per platform

### Test Runner Architecture
- TestMeApp: Main application, owns signal handlers
- TestRunner: Executes tests, receives shouldStop callback
- ServiceManager: Manages background services, owns cleanup handlers
- Clean separation: Each component has single responsibility
