**Reporter:** Internal — hit while writing C unit tests for `~/dev/sec`
(`sec-scan`). A test asserting `teqi(fuzzLoadDir(runner, dir), 3, ...)` reported
3 loaded entries but left **6** in the corpus. The loader ran twice.

**Symptom:** All 30 two-argument comparison macros expand each operand **twice** —
once in the comparison, once in the report call:

```c
/* src/modules/c/testme.h:302 */
#define teqi(a, b, ...)     if (1) { \
                                int _r = (a) == (b); \
                                tReportInt(_r, TM_LOC, a, b, __VA_ARGS__); \
                            } else
```

`a` and `b` each appear twice in the expansion, so any operand with a side
effect runs twice. Affected (every macro taking `(a, b, ...)`):

```
teqi teql teqll teqz tequ teqp teq
tneqi tneql tneqll tneqz tnequ tneqp tneq
tgti tgtl tgtll tgtz tgtei tgtel tgtell tgtez
tlti tltl tltll tltz tltei tltel tltell tltez
```

The single-argument macros are **correct** and show the intended pattern —
`ttrue` (`:460`) and `tfalse` (`:283`) evaluate `E` once into `_r` and then
report `_r`, never `E`.

**Why this is worse than an ordinary macro-hygiene nit:** the failure is
*silent and passes*. In the case above, `fuzzLoadDir` returned 3 both times, so
the assertion was green; the corruption was in the state the rest of the test
then inspected. A double-evaluated `i++`, `read()`, `pop()`, `malloc()` or any
"do the thing and return a count" call produces a test that passes while
testing something other than what it claims. It also silently doubles resource
consumption in the failure-reporting path.

Assertion macros are the one place where a test author is least likely to
suspect their own code, which is why the usual `#define MAX(a,b)` caveat does
not really cover it.

**Steps to Reproduce:**

```c
#include "testme.h"

static int calls = 0;

static int bump(void) { return ++calls; }

int main(void) {
    teqi(bump(), 1, "bump returns 1");   /* passes */
    teqi(calls, 1, "bump was called once");
    return 0;
}
```

Observe: the first assertion passes, the second **fails with `calls == 2`**.
The same shape reproduces for every macro in the list above, and for the second
operand as well as the first.

**Expected Behavior:**

- Each operand is evaluated exactly once per assertion, matching the guarantee
  `ttrue`/`tfalse` already provide.

**Suggested Fix:**

Hoist both operands into temporaries, exactly as the single-argument macros
already do. The temporaries also fix the reporting path, which currently
re-evaluates in order to print:

```c
#define teqi(a, b, ...)     if (1) { \
                                int _a = (a); \
                                int _b = (b); \
                                int _r = _a == _b; \
                                tReportInt(_r, TM_LOC, _a, _b, __VA_ARGS__); \
                            } else
```

Each family already knows its operand type from the `tReport*` it calls
(`int` / `long` / `long long` / `size_t` / `unsigned` / `void*`), so the
temporary's type is mechanical per macro. `teq`/`tneq` (string compare) need
`cchar*` temporaries.

The `if (1) { ... } else` wrapper stays as-is — it already gives the macros
statement-safety and the dangling-`else` guard.

**Files to Investigate:**
- `src/modules/c/testme.h:302-460` — the `teq*` / `tneq*` families
- `src/modules/c/testme.h:472-560` — the `tgt*` / `tlt*` families
- `src/modules/c/testme.h:283`, `:460` — `tfalse` / `ttrue`, the correct pattern to copy

**Verification Criteria:**

1. The reproducer above passes both assertions — `calls == 1` after
   `teqi(bump(), 1, ...)`.
2. A counting-side-effect test covering one macro from each family
   (`teqi`, `teqz`, `teqp`, `tneqi`, `tgti`, `tltz`, `teq`) asserts single
   evaluation of **both** operands.
3. Existing test suites still pass, and failure messages still print the actual
   and expected values correctly.

**Downstream note:** `~/dev/sec` had four assertions affected by this; they were
worked around by hoisting the calls into locals before the assertion. Any other
C suite using these macros may have silently-wrong tests — worth a grep for a
function call appearing directly as a `teq*`/`tneq*`/`tgt*`/`tlt*` operand once
this is fixed.
