**Symptom:** The C compile cache is keyed on the `.tst.c` file alone. A header the test includes can
be edited arbitrarily — including into something that cannot compile — and TestMe reuses the cached
binary and reports a pass.

**Steps to Reproduce:**
1. In a project with a C test that includes a local header (`~/dev/servers/appweb/test/ws/frames.tst.c`
   includes `wsclient.h`), run `tm ws/frames` once so the binary is cached.
2. Append `#error PROBE` to `wsclient.h`.
3. `tm ws/frames`
4. Observe: `✓ PASS ws/frames.tst.c (2.04s)`. Expected: a compilation failure.

The cache reports its decision as "Using cached binary (source unchanged)", which is true of the
`.tst.c` and false of the translation unit.

**Why it matters more than a stale build usually does.** The failure is not "my change did not take
effect" — that would be noticed. It is a **green run that did not test the code**, and it is worst
exactly when a header is being used well: a shared header is the only way to factor common C out of
several tests, because each `.tst.c` is compiled as a standalone translation unit with no link step.
So the practice TestMe forces on C tests is the practice its cache cannot see.

Observed live in appweb: a fix to a helper in `test/ws/wsclient.h` appeared not to work, then
appeared to work intermittently, because some runs used a binary built before the fix. The apparent
flakiness cost more than the original bug.

**Expected Behavior:** A change to any file the test includes invalidates the cached binary.

**Possible approaches, cheapest first:**
- **Depfile.** Compile with `-MMD -MF <cache>/<test>.d` and treat every path in the resulting
  makefile fragment as an input. This is exact, costs nothing at run time, and is what the compiler
  is already able to tell us. `cc` and `clang` both support it; MSVC has `/showIncludes`.
- **Directory mtime.** Hash the mtimes of every `.h` beside the test. Cheap and approximate: it
  misses headers included from elsewhere and rebuilds when an unrelated header is touched.
- **Disable the cache for tests that include a local header.** Correct and wasteful.

The depfile approach also fixes the same hole for a `.tst.c` that includes another `.c`.

**Files to Investigate:**
- `src/handlers/` — the C handler and wherever "source unchanged" is decided
- `src/artifacts.ts` — cache key computation

**Verification Criteria:**
1. Repeat the reproduction: after step 2, the run must fail to compile.
2. Editing a header that the test does not include must not force a rebuild.

**Workaround until fixed:** `rm -rf <dir>/.testme` after editing a shared header. Recorded in
`~/dev/servers/appweb/test/ws/wsclient.h`, which is the header this was found on.

**Root Cause:** `needsRecompilation()` stat'ed the `.tst.c` and the binary, and nothing else. Neither the headers the translation unit pulled in nor the libraries the link read were known to the cache, so both could change freely under a binary the cache still called current.

**Fix Applied:** The compile now records every file the binary was built from, and the cache checks the binary against all of them. Both halves of the ticket are covered by one record, because the cache decision is the same loop either way.

- `src/utils/dependencies.ts` (new) — `DependencyTracker`: the depfile arguments per compiler, a makefile-fragment depfile parser, an MSVC `/showIncludes` parser, the link-input resolver, and the `inputs.json` sidecar.
- `src/handlers/c.ts:152-155`, `:263`, `:298` — compiles with `-MMD -MF <artifact>/<test>.d` (`/showIncludes` under MSVC) and resolves the link inputs from the fully expanded flags.
- `src/handlers/c.ts:377-392` — after a successful compile, writes `inputs.json` with the headers and link inputs.
- `src/handlers/c.ts:517-568` — `needsRecompilation()` rebuilds if the binary is missing, if no record exists, or if any recorded input is newer than the binary or has gone.
- `src/handlers/c.ts:145` — the cache message now reads "Using cached binary (inputs unchanged)". The ticket is right that "source unchanged" was true of the `.tst.c` and false of the translation unit.

**Link inputs.** Resolved from the test's own `-L`/`-l` and `/LIBPATH:` settings plus any explicit `.a`/`.o`/`.so`/`.dylib`/`.lib`/`.obj` path on the command line, and only paths that exist are recorded. System libraries are deliberately not tracked: they do not change between two runs of a suite, and stat'ing them on every test would cost more than it saves. This is the `~/dev/ioto/json` case from the 2026-09-03 evidence — `-L../build/bin -ljson` now records `libjson.a`, so rebuilding the library relinks the tests.

**MSVC.** `/showIncludes` writes the header list to stdout; those lines are lifted out before the compile output is shown or logged, matched by the source path they end with rather than by the note's prefix, which is localized. If the parse finds nothing the behaviour is exactly what it was before this change, never worse. This path is not exercised by the suite - no MSVC toolchain was available.

**Tests Added:** `test/compile-cache.tst.ts` (22 assertions), driving `tm` over `test/cache/` and `test/cache-lib/`:
- the included header is recorded in `inputs.json`; an unchanged test reuses its cached binary; a header the test does not include does not force a rebuild
- the ticket's reproduction: a header edited to `#error PROBE` forces a rebuild and fails the run with the compiler's message
- `DependencyTracker.resolveLinkInputs()` resolves a `-l` library under a `-L` directory and an explicit object path, and records neither when the file does not exist
- end to end: a static library is built, linked and cached, then rebuilt to return a different value - the test relinks and fails, where before it reran the stale binary and passed. Needs `ar`, so it is not run under MSVC; the resolver checks above cover the compiler-independent part.

Run with `make test`. Verified failing against the unfixed cache ("an edited header forces a rebuild") before passing against the fix.

**Verification:** Full suite 55 passed / 1 skipped / 408 assertions.

**Not done:** a change to the compile command itself (different flags, a different compiler) still does not invalidate the cache. It did not before either, and it is outside what this ticket describes; recording the command line beside the inputs would close it.

**Investigation History:**
- 2026-09-11: **FIXED** - the compile records its headers (depfile) and link inputs in `inputs.json`, and the cache checks the binary against all of them. Added `test/compile-cache.tst.ts`.
- 2026-08-31: Found while factoring the appweb WebSocket tests onto a shared `wsclient.h`
  (appweb #10366). Reproduced deterministically with `#error`.

**Additional evidence: linked libraries, not just headers (2026-09-03).** The same cache decision
also ignores every library the test links, which is the more common case for a project whose tests
exercise a library rather than a header.

Observed in `~/dev/ioto/json`: five parser defects were fixed in `src/jsonLib.c`, `make test`
reported 40/40 green, and one of the new assertions should have failed. It only surfaced after
`rm -rf test/.testme` forced a relink — the run had been executing binaries built against the
previous library. Every green result taken during that session was suspect and had to be re-verified.

This is worse than the header case in one respect: a header edit is usually part of the change you
are testing and its absence is eventually noticed, whereas a library change is the *whole point* of
the test run, so the cache is blind precisely when it matters most.

The depfile approach proposed above covers headers but not libraries — `-MMD` records includes, not
link inputs. A complete fix needs the link inputs too: the resolved `-l`/`-L` libraries and any
explicit object or archive paths, stat'ed alongside the depfile entries.

`~/dev/ioto/json` works around it in its own Makefile, clearing `test/.testme` when
`build/bin/libjson.a` is newer than the last run. That is a per-project workaround for something
every C project using TestMe needs.
