**Symptom:** The `Assertions: N/N passed` line in the run summary is not a stable function of the
tests that ran. Running the same 91-test suite (Embedthis GoAhead, `~/dev/servers/goahead/test`)
reports **12352** assertions on some runs and **4348** on others, with the same tests, the same
binaries and per-test durations that match to within noise.

The pass/fail verdict is correct in every run. Only the assertion tally moves. That matters because
the tally is quoted as coverage evidence - it appears in release test reports and in issue records
as "12352/12352 assertions passed", and it is not a number anyone can reproduce.

**Measured, repeatedly:**

| Invocation | Tests | Assertions | Failures |
|---|---|---|---|
| `tm` | 91 | 12352 | 0 |
| `tm` (repeat) | 91 | 12352 | 0 |
| `tm --depth 1` | 91 | 12352 | 0 |
| `tm --clean` then `tm` | 91 | 12108 | 4 |
| `tm --depth 5` | 91 | 4348 | 1 |
| `tm --depth 9` | 91 | 4348 | 1 |
| Sum of the same tests run as ~10 smaller groups | 91 | ~4386 | 0 |

Per-test durations were captured for a `--depth 0` run and a `--depth 5` run and diffed: the largest
difference is 1.3 s on a 5.7 s test and everything else is noise. **No test did materially more or
less work.** Yet the reported assertion totals differ by a factor of 2.8.

Note the last row. When the same 91 tests are run in smaller groups and the per-group totals are
added, the sum (~4386) agrees with the *low* figure, not the high one. That is the strongest
available evidence that **4348 is the honest count and 12352 is inflated**, but it is evidence, not
proof, and the mechanism is not yet identified.

**Where the count comes from:**

- `src/utils/assertion-counter.ts` - `countAssertions(output)` counts lines matching
  `/^\s*([✓✗])(?:\s|$)/gm` in a single test's captured output.
- `src/handlers/base.ts:503` - `createTestResult` calls it on the combined stdout/stderr for that
  test, and stores the result on the `TestResult`.
- `src/reporter.ts:298` - `calculateStats` sums `result.assertions.passed` over the results array.

`stats.total` comes from the same reduce over the same array and reports 91 in every run above, so
the array is not gaining or losing entries. Therefore individual `result.assertions` values must be
differing between runs - which is what needs explaining, given that the tests behaved identically.

**Two candidate mechanisms, neither confirmed:**

1. `^\s*` in the counting regex can span line boundaries, because `\s` matches `\n`. A run of blank
   lines before a marker is consumed as part of the match. `matchAll` advances past each match so a
   marker should not be counted twice, but the interaction with `(?:\s|$)` and `m` deserves a direct
   test with adversarial spacing.
2. Output attribution. If any output that is not a single test's own can reach that test's
   `output` string - a service script, a shared log, a streamed buffer - its markers are counted
   against it. The C handler already combines compile output with run output
   (`combineOutputs(compileResult.output, result.stdout, result.stderr)`), which is the one place a
   result's output demonstrably contains something the test itself did not print.

**Ruled out:**

- **Artifact accumulation across runs.** `tm --clean` followed by three consecutive full runs gave
  12108, 12352, 12352. The count does not grow with repetition.
- **A failing test truncating the tally.** A 15-test group containing the same failing test reported
  1938 assertions with and without the failure.
- **Test-count differences.** 91 in every run.

**Impact:** The `Assertions:` line cannot be used as a coverage metric or as release evidence by any
project using TestMe. It is currently cited that way. Either the number should be reproducible, or
the summary should stop presenting it as one.

**Files to Investigate:**
- `src/utils/assertion-counter.ts` - the regex and its multi-line behaviour
- `src/handlers/base.ts:495-530` - `createTestResult`, and what `output` contains per handler
- `src/handlers/c.ts:85` - `combineOutputs(compileResult.output, ...)`
- `src/reporter.ts:277-320` - `calculateStats`

**Verification Criteria:**
1. `countAssertions` has unit tests covering: markers at line start, indented markers, markers
   preceded by blank lines, markers embedded mid-line (must not count), markers inside a quoted
   expected/received value (must not count), and CRLF input.
2. Running the same suite twice with no source change reports the same assertion total.
3. Running a suite in one invocation reports the same total as the sum of running its tests in
   groups.
4. A regression test in TestMe's own suite pins the count for a fixture whose expected number of
   markers is known by construction.

**Related:**
- [#10002](10002.md) - `tskip()` reports a skipped test as PASS with zero assertions. Same theme:
  the summary's headline numbers do not mean what a reader takes them to mean.
- [#10000](10000.md) - C assertion macros double-evaluate their operands; its second verification
  criterion is a counting-side check.

## Resolution

**The counter is exact. The tally moves because the tests print a different number of markers.**
No production code was changed; the work was to prove that and to pin it with tests.

**Neither candidate mechanism was the cause.**

1. *The regex.* `countAssertions` was probed directly against all six shapes named in the criteria —
   markers at line start, indented, behind one or more blank lines, mid-line, quoted as
   Expected/Received values, and CRLF — plus adjacent bare markers and two markers on one line. It is
   correct in every case. `\s*` does span line boundaries, but `matchAll` advances past each match,
   so a marker is never counted twice and never swallowed. Disproved.
2. *Output attribution.* GoAhead's suite runs `parallel: false`, so no two tests' output can
   interleave, and the counts below are per-file. Disproved for this suite.

**What the instrumented run showed.** `reportProgress` was temporarily made to print
`result.assertions` per file (the step this ticket proposed) and the GoAhead suite was run twice,
back to back, with no source change: 3910/3915 then 3993/3995 over 93 files. Only four files moved:

| File | Run 1 | Run 2 |
|---|---|---|
| `regress/cgi-content-length-honesty.tst.ts` | 0 | 57 |
| `regress/cache-control-status.tst.ts` | 26 | 47 |
| `regress/cgi-timeout-detach.tst.ts` | 2 | 3 |
| `session/exhaust.tst.ts` | 1348 | 1352 |

The other 89 files reported identical counts. Two causes, and between them they account for every
row of the measurement table above:

- **A failing test truncates its own tally.** The JS assertion helper calls `process.exit(1)` on the
  first failing assertion (`src/modules/js/index.js:144`), so a test that fails stops printing
  markers at the point it failed and never reaches the rest. The first three files above failed in
  run 1 and passed in run 2. This is the whole of `12352` (0 failures) versus `12108` (4 failures),
  and most of the drop to `4348` (1 failure) at depth 5.
- **A test's assertion count can depend on state earlier tests left behind.**
  `session/exhaust.tst.ts` opens sessions until the server's table is exhausted, so it emits as many
  markers as there was room for. Run on its own it reports **1564**; inside the full suite, 1348 and
  1352. That is why the whole run does not equal the sum of its parts — the "~4386 in ~10 groups"
  row — and it is a property of the test, not of the counting.

This overturns the "Ruled out" entry above. A failing test *does* truncate the tally; the 15-test
group that reported 1938 either way happened to contain a test that failed on its last assertion, so
there was nothing left for it to skip. The per-file counts are the direct measurement and they are
unambiguous.

**On `--depth`.** GoAhead has six depth-scaled tests (`soak`, `stress/huge`, `stress/upload`,
`security/dos`, `regress/keepalive-hammer`, `leak/valgrind`). `--depth` changes the work they do, so
a depth-0 total and a depth-5 total are totals over two different workloads and were never
comparable. Depth 5 and depth 9 agreeing exactly is the `Math.min(tdepth(), len - 1)` clamp inside
those tests, not a ceiling in TestMe.

**So the summary line means:** the number of `✓`/`✗` result lines the tests actually printed. It is
reproducible for a fixed set of test outcomes and it is not compositional, because a test may print
a number of markers that depends on its own outcome and on the state it inherits. It is a count of
reported assertions, not a coverage denominator, and a run with failures always under-reports.

**Not this ticket:** the 4-failure `--clean` row was traced to a separate defect — a setup service's
backgrounded server surviving the run and blocking the next one, filed as
[#10005](10005.md).

**Tests added:**
- `test/assertion-counter.tst.ts` — seven new unit cases covering every shape in criterion 1:
  line-start, indented, behind blank lines, adjacent bare markers, mid-line (must not count), quoted
  Expected/Received values (must not count), CRLF, and two markers sharing a line.
- `test/assertions/` — `known-count.fixture.ts` (7 markers through the real assertion helper) and
  `adversarial-spacing.fixture.ts` (3 countable markers among decoys), with a `testme.json5` whose
  `**/*.fixture.ts` pattern keeps them out of the parent suite.
- `test/assertion-total.tst.ts` — drives `tm` over that directory and asserts the three properties:
  the tally equals the 10 markers known by construction (criterion 4), two identical runs agree
  (criterion 2), and running the fixtures one at a time and adding the totals gives the same number
  (criterion 3).

Both test files were verified to **fail** against a mutated counter (regex changed to count every
glyph) and to pass against the real one. Full suite: 53 tests, 288/288 assertions, PASSED
(`make test`).

**Verification criteria:** 1 met. 2 and 3 met for deterministic tests and pinned by
`assertion-total.tst.ts`; they cannot hold for GoAhead's suite while `session/exhaust.tst.ts`
emits a state-dependent number of markers, which is correct behaviour for that test. 4 met.
