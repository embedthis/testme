**Symptom:** The C comparison assertion macros in `src/modules/c/testme.h` expand their arguments
twice — once to compute the pass/fail result, and again inside the `tReport*` helper that formats
the report. The formatting is unconditional, so the second evaluation happens on a *passing*
assertion too.

```c
#define teqi(a, b, ...)     if (1) { \
                                int _r = (a) == (b); \
                                tReportInt(_r, TM_LOC, a, b, __VA_ARGS__); \
                            } else

#define tReportInt(success, loc, received, expected, ...) \
    if (1) { \
        char ebuf[80], rbuf[80]; \
        snprintf(ebuf, sizeof(ebuf), "%d", (int)(expected)); \
        snprintf(rbuf, sizeof(rbuf), "%d", (int)(received)); \
        tReport((int) (success), loc, ebuf, rbuf, "" __VA_ARGS__) ; \
    }
```

Any call with a side effect therefore runs twice, and the test silently observes state that the
test author did not create.

**Steps to Reproduce:**
1. Write `teqi(pushItem(list, "a"), 1);` where `pushItem` appends and returns the new index.
2. The assertion passes — `pushItem` returned 1 the first time.
3. Observe: the list now holds **two** items. Every later assertion about the list is wrong, and
   the failure surfaces several lines away from the macro that caused it.

This was hit for real writing HPACK table tests in the `http` project
(`~/dev/servers/http/test/api/hpack.tst.c`): `teqi(httpAddPackedHeader(table, k, v), 62)` inserted
two entries, so the following bounds assertion — that the next index is out of range — failed
because the extra entry had made it valid. The bug looked like a defect in the code under test.

**Expected Behavior:**
- An assertion macro evaluates each argument exactly once, whatever the outcome.
- Assign each argument to a local inside the macro's `if (1) { ... }` block and both compare and
  report from the locals. The macros already declare locals (`int _r`), so the shape is there.
- The types differ per macro (`teqi` int, `teqz` ptrdiff_t, `tmatch` const char*, `teqp` void*),
  so each needs a local of its own type rather than one shared helper.

Affects at minimum: `teqi`, `teql`, `teqll`, `teqz`, `tequ`, `teqp`, `tneqi`, `tneql`, `tneqll`,
`tneqz`, `tnequ`, `tneqp`, `tgt*`, `tlt*`, `tmatch`, `tcontains`. `ttrue` and `tfalse` are already
correct — they evaluate into `_r` and report a constant string.

**Files to Investigate:**
- `src/modules/c/testme.h` — the `t*` comparison macros and the `tReport*` helper macros

**Verification Criteria:**
1. Write a test using `teqi(counter++, 0)` with `counter` starting at 0.
2. Verify: the assertion passes and `counter` is 1, not 2.
3. Repeat for `tmatch(nextToken(), "a")` where `nextToken` advances a cursor.
4. Verify: the existing C test suite still passes unchanged.

**Investigation History:**
- 2026-08-07: Filed after the double evaluation produced a false failure in the `http` project's
  new HPACK tests. Worked around there by hoisting every mutating call into a local before the
  assertion, and by noting the hazard in a comment at the top of the file.
