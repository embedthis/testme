**Symptom:** After a run whose `services.setup` script backgrounds a server, the server is still
alive and still bound to its ports when `tm` exits. The next run's setup then cannot bind, TestMe
reports `Failed to start setup service`, and the whole suite fails for no fault of any test.

**Steps to Reproduce:**
1. `cd ~/dev/servers/goahead/test` (its `setup.sh` runs `set -m` and starts `goahead-test &`).
2. `tm` — the suite runs to completion.
3. `lsof -nP -iTCP:18080 -sTCP:LISTEN` — observe a `goahead-test` still listening.
4. `tm` again — observe `❌ Error: Failed to start setup service (setup.sh)`.

Reproduced three times in a row on 2026-09-01: every completed run left an orphan, and every
following run failed at setup until the orphan was killed by hand.

**Root cause (probable):** `ProcessManager.killProcessUnix` signals a single pid —
`kill -TERM <pid>` then `kill -KILL <pid>` — even though `ServiceManager.killSetup`'s doc comment
says it "kills entire process tree on Unix". The setup script is a shell whose server is a separate
child; with `set -m` the shell puts that child in its own process group, so a signal to the shell
never reaches it. Killing the negated pid (`kill -TERM -<pgid>`, after `Bun.spawn` is asked for its
own process group) is the usual fix. The Windows path already does this — `taskkill /T` walks the
tree.

**Why it matters:** the failure does not look like an environment problem. It surfaces as a run
whose tests fail in unrelated files, which is how it was found: the 4-failure data point in
[#10004](10004.md)'s measurement table is this, not a test defect. It also makes any two consecutive
runs of a service-backed suite non-comparable, which is exactly what #10004 set out to measure.

**Expected Behavior:** when TestMe has torn down a setup service, nothing that service started is
still running, and a second consecutive run starts cleanly.

**Files to Investigate:**
- `src/platform/process.ts:85` — `killProcessUnix`, which signals only the given pid
- `src/services.ts:850` — `killSetup`, whose comment claims a process-tree kill
- `src/services.ts:433` — where the setup process is spawned, and whether it asks for its own group

**Verification Criteria:**
1. Run a suite whose setup script backgrounds a long-lived server; after `tm` exits, no descendant
   of the setup script is still running and its ports are free.
2. Two consecutive runs of that suite both start their setup service successfully.
3. A setup script that exits gracefully on SIGTERM still gets the chance to (no unconditional
   SIGKILL before `shutdownTimeout`).

**Root Cause:** Two defects, either of which alone leaves the orphan.

1. **The teardown was never reached.** `index.ts` guarded the `runCleanup()` call on `services.cleanup` being configured, and `runCleanup()` guarded on it again before killing the setup service. A group that starts a service and configures no cleanup script therefore never tore it down at all. The only remaining path was the `process.on('exit')` handler, which called an `async` cleanup — an exit handler cannot await, so the kill was abandoned mid-flight and nothing was signalled.
2. **The teardown signalled one pid.** As the ticket infers, `killProcessUnix()` sent SIGTERM and SIGKILL to the setup pid alone, while `killSetup()`'s doc comment claimed a process-tree kill. The server holding the ports is a separate process, so the signal never reached it.

**Fix Applied:**

- `src/index.ts:662-668` — the per-group cleanup now runs whenever services are enabled, not only when a cleanup script exists. Same at `:1120` on the error path.
- `src/services.ts:724-736` — `runCleanup()` tears the setup service down before the early return, so the teardown no longer depends on a cleanup script being configured.
- `src/services.ts:985-1000` — the exit handler is now synchronous (`killProcessTreeSync`). The SIGINT/SIGTERM handlers stay async; only `exit` cannot await.
- `src/platform/process.ts:88-135` — `killProcessUnix()` reads the process table with `ps -Ao pid=,ppid=,pgid=`, walks the tree from the setup pid, and signals every descendant deepest first. Where a descendant leads a process group of its own — which is what a shell running with `set -m` produces — it is signalled through that group, so the job's own children are reached too. TestMe's own group is never signalled. Graceful SIGTERM and the `shutdownTimeout` poll are unchanged, except that the poll now waits for every descendant rather than the root alone.
- `src/platform/process.ts:159-211` — `killProcessTreeSync()`, the same walk without awaiting, for the exit path.
- If `ps` is unavailable the walk falls back to the root pid alone, which is exactly the previous behaviour and never worse.

**Tests Added:** `test/service-teardown.tst.ts` (8 assertions) drives `tm` over `test/service-teardown/`, whose setup service backgrounds a separate server process holding port 18099 — the shape the old teardown missed. Checks that after the run the setup process is gone, the server it started is gone, the port is free, and the server was sent SIGTERM before anything forced it (so the graceful path still works); then reruns the same suite, which is the ticket's reproduction, and checks it starts its setup service and passes. The fixture records the pids it creates and the driver kills any survivor on exit, so a failure here cannot poison later runs. Run with `make test`. Verified failing against the unfixed teardown ("the server the setup service started is gone") before passing against the fix.

**Verification:** Full suite 56 passed / 1 skipped / 416 assertions.

**Not done:** a descendant already reparented away from the setup process before teardown — its script exited while leaving the server running — cannot be found by a tree walk. TestMe treats a setup script that exits as a failed service, so this is reported rather than silently orphaned, but it is not killed.
