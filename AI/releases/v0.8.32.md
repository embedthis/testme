# TestMe v0.8.32 Release Notes

Released: 2025-12-10

## Enhancements

### --clean Runs Cleanup Service Scripts

The `--clean` flag now runs cleanup service scripts defined in `testme.json5` configurations before removing `.testme` artifact directories.

**Previous Behavior:**

`tm --clean` only removed `.testme` artifact directories containing compiled binaries and build logs.

**New Behavior:**

`tm --clean` now:

1. Recursively finds all `testme.json5` files in the directory tree
2. Runs each config's cleanup script (if defined)
3. Removes `.testme` artifact directories

**Use Cases:**

- Clean up test-generated files (temp files, logs, uploads)
- Kill background processes that tests may have started
- Reset test environment to pristine state
- Prepare for fresh test runs after debugging

**Example:**

With a `testme.json5` containing:

```json5
{
    services: {
        cleanup: 'cleanup.sh',
    },
}
```

And a `cleanup.sh` that removes temp files:

```bash
#!/bin/bash
rm -rf tmp/*
rm -f *.log
```

Running `tm --clean` now produces:

```
Cleaning test artifacts...
✓ Cleanup completed successfully: cleanup.sh
✓ All test artifacts cleaned
```

- [src/index.ts:1024-1032](src/index.ts#L1024-L1032) - Updated `--clean` handler

### Visual Studio Project Generation for --debug on Windows

The `--debug` flag on Windows now generates a proper Visual Studio project (`.vcxproj`) with environment variables configured for DLL loading.

**Previous Behavior:**

`tm --debug test.tst.c` on Windows used `devenv /UseEnv /DebugExe <binary>`, but `/UseEnv` only affects compilation, not the debugger environment. This caused DLLs to fail to load because PATH wasn't available to the debugger.

**New Behavior:**

`tm --debug test.tst.c` now:

1. Generates `<testname>.vcxproj` with compiler settings (include paths, library paths, etc.)
2. Generates `<testname>.vcxproj.user` with debug settings including `LocalDebuggerEnvironment` for PATH and other environment variables
3. Opens Visual Studio with the project

**Key Features:**

- Environment variables (including PATH for DLL loading) are persisted in the `.vcxproj.user` file
- Working directory is set to the test directory
- Include and library paths are properly configured
- All TESTME_* variables and user-defined environment variables are included
- No external tool required (unlike xcodegen on macOS)

**Example Output:**

```

📂 Working Directory: C:\project\test
📝 Created Visual Studio project: socket.vcxproj

🚀 Launching Visual Studio...
✅ Visual Studio launched

To debug:
1. Visual Studio should be open with the project loaded
2. Build the project (Ctrl+Shift+B)
3. Set breakpoints in: C:\project\test\socket.tst.c
4. Start debugging (F5)

```

## Bug Fixes

### Node.js 18 Compatibility for Postbuild Script

Fixed `bin/postbuild.mjs` to work with Node.js 18.x on Linux.

**Issue:**

The postbuild script used `import.meta.dirname` which is only available in Bun and Node.js 20.11+. On Linux with Node.js 18.19.0, this caused the build to fail with:

```
TypeError [ERR_INVALID_ARG_TYPE]: The "paths[0]" argument must be of type string. Received undefined
```

**Fix:**

Replaced `import.meta.dirname` with the standard ESM approach using `fileURLToPath(import.meta.url)` which works across all Node.js versions that support ESM.

**Implementation Files:**

- [bin/postbuild.mjs](bin/postbuild.mjs) - Updated to use cross-platform directory resolution
